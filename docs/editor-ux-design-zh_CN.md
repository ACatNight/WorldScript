# WorldScript Editor UX Design

## 1. 定位

WorldScript Editor 是面向 Minecraft RPG 服务器管理员的聊天式区域编辑器。

它不是后台管理面板，也不要求管理员记忆完整配置语法。编辑器应让管理员在游戏内完成：

1. 创建和查看区域。
2. 配置进入、离开、交互和方块点击事件。
3. 配置区域发现、条件和首次奖励。
4. 预览并验证动作结果。

## 2. 视觉方向

### Dark Fantasy System

- 背景：深黑、深蓝，避免大面积纯黑导致内容消失。
- 主色：金色，用于区域身份、标题和重要状态。
- 功能色：青色，用于可编辑字段和动作参数。
- 成功色：绿色，用于启用、保存和条件满足。
- 警告色：黄色，用于继承、未配置和需要确认的操作。
- 危险色：红色，用于删除、拒绝进入和关闭功能。
- Discovery：紫色，代表探索和首次发现。

### 文本层级

```text
WorldScript > 区域名称 > 当前页面 > 分组 > 属性 > 操作
```

每一页只保留一个主要任务，避免把所有配置堆在同一屏。

## 3. 编辑器信息架构

### 基础模式

```text
基础信息
区域状态
进入事件
区域发现
进入条件
```

### 高级模式

```text
变量
动作参数
继承来源
冷却时间
触发模式
Placeholder
Kether
```

基础模式用于快速配置，高级模式只在管理员主动进入变量、动作参数或高级设置时出现。

## 4. 页面设计

### 区域主页

显示：

- 区域名称和 ID
- 世界和坐标范围
- 当前状态
- 父区域和子区域数量
- 继承状态

### 事件页面

每个事件使用统一结构：

```text
事件名称
启用状态
触发模式
冷却时间
动作数量
[打开]
```

### 动作页面

所有动作使用同一套编辑流程：

```text
动作类型
动作值
参数列表
预览
删除
```

Discovery 奖励、Enter、Leave、Interact、左键方块和右键方块都必须复用该流程。

### 条件页面

条件应显示为可读列表：

```text
组合方式：ALL

1. Placeholder
   %your_placeholder% >= 10

2. Permission
   region.enter.mine
```

条件失败时提供：

- 聊天提示
- 可配置 Title
- 可配置副标题
- 失败原因

## 5. 交互原则

### 渐进式复杂度

- 默认先显示基础属性。
- 只有点击动作后才显示参数。
- 只有进入高级页面才显示变量、继承和 Kether。

### 统一动作

动作类型必须来自同一个动作目录，不为 Discovery、Enter 或其他事件创建特殊输入语法。

### 明确反馈

每次保存、删除、切换和预览都必须立即返回结果：

```text
已保存
已删除
已启用
已关闭
预览成功
配置无效
```

### 可恢复操作

- 删除动作必须二次确认。
- 聊天输入支持 `cancel` 和 `取消`。
- 继承动作第一次编辑时自动创建本地副本。
- 页面刷新不会丢失已保存内容。

## 6. `/ws list` 交互约定

该交互不可改变：

- 左键区域：打开编辑器。
- 右键区域：传送到区域中心。
- 中键区域：打开全局设置。
- 顶部地图按钮：作为中键不可用时的全局设置备用入口。

## 7. 配置开关原则

所有玩家体验功能默认关闭：

- Discovery
- Discovery Title
- Discovery Sound
- Discovery Reward
- Discovery GUI
- Entry Conditions

编辑器开启区域功能时，可以自动打开对应全局开关，但不能强制玩家打开 Discovery GUI 或 Codex。

## 8. 开发拆分计划

1. `RegionActionStore`：动作数据访问和继承。
2. `EditorInputParser`：输入解析。
3. `EditorSessionStore`：聊天会话状态。
4. `EditorRenderer`：页面和属性展示。
5. `EditorActionController`：动作增删改和参数预览。
6. `EditorConditionController`：条件编辑和失败反馈。
7. `EditorDiscoveryController`：发现设置和发现动作。

当前已完成前 3 项，后续拆分必须保持功能测试和 `/ws list` 交互不变。

## 9. 设计审核清单

每个新增功能必须回答：

1. 是否降低管理员学习成本？
2. 是否支持高级用户继续扩展？
3. 是否可以单独关闭？
4. 是否符合 RPG 服务器的区域、事件和进度流程？
5. 是否能复用现有动作、条件和 Placeholder 系统？
6. 是否有明确的保存、失败和预览反馈？
7. 是否能在聊天界面中保持可读？
